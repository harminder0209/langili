# Secure Sandcastle activation from GitHub

Research for “Verify secure Sandcastle activation from GitHub,” conducted 2026-09-27 against current first-party Sandcastle and GitHub documentation.

## Decision

Use an `issues:labeled` GitHub Actions workflow as a narrow authorization gate. Accept an event only when all of these immutable/event-specific facts match:

- `github.repository == 'harminder0209/language_app'`;
- `github.event.action == 'labeled'`;
- `github.event.label.name == 'ready-for-agent'`;
- the payload is an issue, not a pull request (`github.event.issue.pull_request == null`);
- `github.event.sender.id` is `16590167` (`harminder0209`) or `25961770` (`singhpankaj99`); and
- the issue is still open and still has `ready-for-agent` when fetched afresh through the API.

GitHub documents `issues` with the `labeled` activity as the event for this trigger and recommends a job condition on the label name ([triggering a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#using-activity-types-and-filters-with-multiple-events)). Use the payload's `sender.id`, not only `github.actor` or a mutable login. GitHub says `github.actor` is the user who triggered the *initial* run and that a rerun may have a different `github.triggering_actor` while still using the original actor's privileges ([contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context)). The numeric IDs above were verified through GitHub's official Users API on 2026-09-27 ([`harminder0209`](https://api.github.com/users/harminder0209), [`singhpankaj99`](https://api.github.com/users/singhpankaj99)); the workflow should keep both ID and expected login in its audit record, but authorize on ID.

Do not accept `workflow_dispatch`, `issue_comment`, a mere present-day label, or a rerun as fresh authorization. The authorizing fact is the particular `labeled` timeline event generated by an allowlisted account. GitHub issue events expose a unique event `id`, `actor`, event type, and timestamp ([issue event types](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types#issue-event-object-common-properties)). Re-fetch the issue's events and require a matching `labeled` event for `ready-for-agent`, the allowlisted actor ID, and the webhook delivery's issue. This gives the gate a stable authorization ID rather than trusting mutable issue text.

## One approved ticket, one invocation

Set workflow concurrency to a repository-and-issue-specific group, for example `sandcastle-${{ github.repository_id }}-${{ github.event.issue.id }}`, with `cancel-in-progress: false`. GitHub concurrency ensures only one member of a group runs at a time, but by itself it is not a durable exactly-once primitive: pending runs can be replaced and ordering is not guaranteed ([workflow concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)).

Inside that serialized section:

1. Re-fetch the issue and the exact label event.
2. Search issue comments for a machine-readable claim keyed by the label event ID, such as `<!-- sandcastle-authorization:event=123;issue_id=456 -->`.
3. If a claim already exists, exit successfully without starting Sandcastle.
4. Create the claim comment before launch. Include actor login and numeric ID, label-event ID and timestamp, issue number and node/database ID, Actions run URL/ID/attempt, and workflow commit SHA.
5. Invoke `sandcastle.run()` exactly once with an explicit prompt containing only this issue's fetched snapshot, a unique name such as `issue-<number>-event-<event-id>`, and `maxIterations: 1`.
6. Update the issue with the terminal result (branch/commit or failure) and the same authorization ID. Remove `ready-for-agent` and apply the chosen in-progress/completed state using the workflow token so that these mutations do not recursively start another workflow.

Sandcastle documents `run()` as a single agent invocation and `maxIterations` as defaulting to `1`; set it explicitly so later config changes cannot widen the run ([Sandcastle `RunOptions`](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/README.md#runoptions)). Avoid the `simple-loop` template here: the required unit is the already-authorized issue, not an agent-selected queue. Pass the exact issue number and authorization ID into a purpose-built prompt and prohibit querying for another ticket.

This design gives **at-most-once start** for each accepted label event and exactly one Sandcastle invocation on the successful path. No GitHub Actions design can atomically persist a GitHub comment and start an external agent, so a crash after claiming but before launch can yield zero starts. Automatically retrying that gap can instead yield two starts if the launch occurred but its acknowledgement was lost. Recovery should therefore require a human to remove and reapply `ready-for-agent`, producing a new, auditable authorization event. This limitation should be stated rather than promising strict distributed exactly-once execution.

## Handling untrusted issue content

Treat the issue title, body, comments, labels, and author-controlled fields as hostile data. GitHub explicitly identifies issue titles/bodies and other context fields as script-injection risks and recommends using an intermediate environment variable or an action instead of interpolating expressions into shell scripts ([script injections](https://docs.github.com/en/actions/concepts/security/script-injections)). In practice:

- fetch the issue JSON with the API using the numeric issue identifier from the event;
- write/transform it with a JSON-aware program, never `eval`, shell interpolation, command substitution, or a generated workflow/script;
- pass scalar IDs as validated decimal strings and pass text through a file or stdin;
- check out only the trusted default-branch commit associated with the workflow, never a ref named in issue content;
- place issue content in clearly delimited prompt data and explicitly say it is untrusted requirements text, not instructions about credentials, authorization, ticket selection, or orchestration; and
- assume prompt injection can still control the coding agent. The real defense is capability restriction and sandboxing, not delimiters.

Sandcastle describes itself as running agents in isolated Docker, Podman, or Vercel sandboxes and warns that `noSandbox()` runs directly on the host ([Sandcastle README](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/README.md#sandbox-providers)). Use an isolated provider, a non-root container user, no Docker socket or host credential mounts, a disposable worktree, resource/time limits, and—if feasible—network egress allowlisting. Do not use `noSandbox()` for a public-issue-triggered agent.

## Permissions and secrets

Start the workflow with `permissions: {}`. GitHub documents that specifying any permission makes every omitted permission `none`, and supports permissions at job scope ([workflow syntax: `permissions`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)). Split the workflow into jobs so credentials exist only where required:

- **Gate/claim job:** `issues: write` only (write includes read) to read events and create the audit claim. No model secret, no checkout, and no arbitrary repository code.
- **Agent job:** only after the gate output says `accepted`; `contents: write` if it must push a branch, `pull-requests: write` only if it creates/updates a PR, and `issues: write` only if it reports/changes issue state. Do not grant `actions`, `workflows`, `administration`, `id-token`, `packages`, or other scopes unless a concrete operation requires one.

Prefer the job-scoped `GITHUB_TOKEN`, which GitHub says is repository-scoped and expires when the job ends, over a PAT ([compromised runners](https://docs.github.com/en/actions/concepts/security/compromised-runners#stealing-the-jobs-github_token)). If Sandcastle's provider requires `GH_TOKEN`, inject that job token only into the Sandcastle process/sandbox and keep its permissions minimal. Sandcastle lists `GH_TOKEN` plus the selected model credential in provider environment requirements ([agent providers](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/docs/content/docs/agents.mdx)).

The model credential is the hardest secret: an agent influenced by hostile issue text can attempt to print or exfiltrate every secret it can access. GitHub warns that secrets in environment variables are directly accessible to compromised runner code ([compromised runners](https://docs.github.com/en/actions/concepts/security/compromised-runners#accessing-secrets)). Use a dedicated, low-quota/revocable model credential; expose no unrelated repository, cloud, signing, or personal secrets; never print the full `github` context because it contains `github.token` ([contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context)); and use a protected GitHub environment if human approval before secret release is acceptable. Stronger unattended protection requires a credential broker/egress proxy so the sandbox never receives a reusable provider key.

When the workflow removes or changes labels with `GITHUB_TOKEN`, GitHub normally suppresses new workflow runs caused by that token, avoiding recursive activation ([triggering workflows from workflows](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)). Do not replace it with a PAT merely to mutate labels.

## Audit record

The public issue timeline is the canonical authorization trail: it records who applied the label and when, while the claim/result comments bind that event to a workflow run and Sandcastle result. Keep Actions logs as supporting evidence, not the only record, because their retention is configurable. The minimum claim record is:

```json
{
  "schema": 1,
  "authorization": {
    "label": "ready-for-agent",
    "event_id": 123,
    "actor_login": "harminder0209",
    "actor_id": 16590167,
    "created_at": "..."
  },
  "ticket": { "repository_id": 456, "issue_id": 789, "number": 42 },
  "workflow": { "run_id": 1234, "run_attempt": 1, "sha": "...", "url": "..." },
  "state": "claimed"
}
```

Make the marker machine-readable and append-only in meaning: post a separate terminal result or edit only the bot-authored claim while retaining the original authorization fields. Never copy the issue body into the authorization record.

## Remaining uncertainties

- Sandcastle isolates execution but its documentation does not claim that Docker/Podman provides network egress filtering. If model/API access and GitHub access share unrestricted outbound networking, prompt-driven exfiltration remains possible; enforcement must come from runner/network architecture.
- The exact write permissions depend on the delivery contract still to be chosen (push branch, open PR, or produce an artifact). `contents: write` is unnecessary if the agent only creates a patch artifact; `pull-requests: write` is unnecessary if it only pushes a branch.
- If strict “eventually starts exactly once” is mandatory across runner crashes, GitHub issue comments plus Actions are insufficient. A transactional external dispatcher with an idempotency key and durable launch ledger is required.
